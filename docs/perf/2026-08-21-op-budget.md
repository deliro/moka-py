# Op budget: layer-by-layer profile of get / set / get_with

Findings record for the ADR-0003 "budget profile before new optimizations"
step. Measurement artifacts (probe pymethods, probe benches, pure-Rust floor
bench) live on the local branch `scratch/profile-budget` (commits 554fe2d,
5d24d72) and are not meant to be merged; this document records the results
and the verdicts.

Measured 2026-08-21 on a Linux aarch64 VM hosted on the canonical Apple
Silicon machine, CPython 3.13, PYTHONHASHSEED=0, pytest-benchmark
min-time=0.5. Absolute numbers matched the canonical Mac baseline
`0005_7e26d69` within a few ns on every op (get hit 99 vs ~100-107, get_with
miss 989 vs ~980, set fresh 435 vs ~400), so the *shape* of the budget is
trusted; merge verdicts still require the canonical machine.

Instruments: probe pymethods (`probe_*` added to `src/lib.rs` on the scratch
branch), probe benches (`scratch/probe_benches.py`), and a pure-Rust moka
floor bench (`examples/moka_floor.rs`, one suite per process — same-process
suite order was measured to shift results by 5-6ns).

All Python-side numbers include the ~36ns `next(cycle)`+lambda harness floor
(measured directly as `ref_next_only`); layer costs below are differences,
harness excluded.

## get hit (int/short-str needle pool): ~63ns of real work

| layer | ns | note |
|---|---|---|
| CPython -> PyO3 dispatch + arg parse (`key, default=None`) | ~5 | probe_sig_get - ref_next_only |
| `PyObject_Hash` (AnyKey::new_with_gil) | ~2 | int; cached-hash str same; tuple +3.5 |
| moka core read, incl. `AnyKey::eq` richcompare | ~56 | probe_get_drop - probe_hash |
| ...of which `AnyKey::eq` via Python `__eq__` | ~7 | Python 56 vs pure-Rust full ~49 |
| ...of which the always-installed `expire_after` trait | ~5-10 | 2x2 toggle square + Rust floor (bare 37-41 vs full 41-52) |
| ...of which raw concurrent-read machinery | ~30-35 | pure-Rust bare hit ~39 vs plain ahash HashMap 4.7 |
| result INCREF + Option assembly | ~0 | full get == probe_get_drop |

get miss: ~43ns of real work (~5 dispatch + ~2 hash + ~30 moka miss read,
no eq, no read recording).

## set (replace ~300ns total / fresh ~435ns total)

| layer | ns |
|---|---|
| dispatch + 4-arg parse (`key, value, ttl=None, tti=None`) | ~12 |
| prep: weigher-None check, AnyKey, parse_duration x2, `Arc::new`, `Instant::now` | ~15 (of which `Instant::now` ~5) |
| moka `insert` (replace) | ~237 |
| moka `insert` (fresh key + eviction pressure) | ~372 |

Pure-Rust replace insert is ~232-247ns regardless of expiry/weigher/value
layout: the cost is moka's write path itself.

## get_with

Hit: with pool-parity methodology get_with hit == plain get; the entire
inherent residual is ~9ns of extra arg parsing (4-arg signature vs 2-arg,
probe_sig_get_with - probe_sig_get). The larger residual seen in the
canonical matrix (~28ns) is methodology: that bench hammers one identical
needle ("hello", identity-short-circuited eq) instead of a pool.

Miss (~989ns): ~15 parse+hash, ~30 failed `cache.get`, **~98 GIL
detach+attach round-trip** (probe_detach_attach - probe_noop; detach alone
~35), ~7 initializer call, ~15 wrapper prep, ~240 insert-equivalent,
remainder **~570ns inside `try_get_with` coalescing machinery** (waiter-map
registration, second hash/lookup, error-clone plumbing) — all upstream.
The detach is required for correctness (another thread's initializer needs
the GIL; holding it while waiting would deadlock).

## Hypotheses from the handoff: verdicts

- "PyO3 argument parsing is fat" — **no**: ~5ns (get) / ~12ns (set) total,
  including CPython dispatch. Vectorcall + PyO3 fastcall are near-free.
- "`Arc<Py<PyAny>>` double indirection" — **no**: compact `Arc<Inner>`
  (8-byte V) vs 56-byte ValueWrapper differ by ~1ns in pure Rust (the
  earlier apparent 8ns was same-process suite-order noise).
- "get_with hit residual" — explained: ~9ns arg parsing + bench methodology.
- "get_with miss too heavy" — confirmed and attributed: ~58% coalescing
  machinery + ~24% insert (upstream), ~10% GIL round-trip (required).

## Actionable levers, ranked

1. **`expire_after` read tax, ~5-10ns on the target op (get hit ~5-10%).**
   The trait is installed unconditionally because `set(ttl=...)` may arrive
   at any time after construction. No transparent bridge-side removal exists
   within moka's builder-time API. Options (all need an owner decision):
   upstream moka fast-path when the expiry returns "no change", or
   bridge-side per-entry expiry (read-time check) — the latter changes
   observable eviction/listener timing, i.e. new ADR territory.
2. **Sub-threshold transparent batch (~1-2% each):** skip `Instant::now()`
   in `set`/`get_with`-miss prep when no per-entry ttl/tti is passed
   (`created_at` is provably never read then — invariant already documented);
   nothing else bridge-side is left above noise.
3. **Own single-flight for `get_with` miss** could plausibly halve the
   ~989ns, but duplicates moka logic (>=10% bar, owner decision) and the
   miss path is cold by nature (real initializers dwarf 1µs).
4. Everything else — read machinery (~30-35ns), insert (~240ns) — is moka
   core; improvements belong upstream.

Bottom line: after 54a6fdb the bridge adds ~7ns of glue plus ~9ns of
semantically-required Python calls (hash+eq) to a ~40-50ns moka core read.
There is no double-digit transparent win left inside `src/lib.rs` for get/set;
the next material step is either upstream work or an owner-approved semantic
decision on per-entry expiry.

## Addendum: double hashing (PyObject_Hash + ahash), 2026-08-21

The bridge hashes twice per lookup: CPython's `PyObject_Hash` on the key
object (~2ns; str caches its hash, tuple recomputes, ~+3.5ns), then moka's
`ahash::RandomState` over the stored `py_hash` isize. Measured with hasher
variants in `examples/moka_floor.rs` (one suite per process, medians of 3):

| hasher over py_hash | get hit | get miss | insert replace |
|---|---|---|---|
| ahash (current) | 41.0 | 30.7 | 240.9 |
| fib multiply+xorshift | 41.8 | 31.7 | 243.7 |
| identity (drop 2nd pass) | 37.1 | 29.8 | 237.7 |
| identity, int keys strided by 4096 | **1235** | **2490** | **1757** |
| ahash, same strided keys | 40.7 | 31.3 | 236.3 |

Verdict: the second pass costs ~4ns (~4% of a real get hit) and is
load-bearing. CPython hashes ints to themselves; moka's cht needs dispersed
bits, so identity hashing turns perfectly ordinary aligned/rounded int keys
(stride 4096 here) into a 30-80x cliff, plus it reopens hash-flooding.
A cheaper mixer buys nothing: one multiply+xorshift already matches ahash
on a single u64 (aarch64). Skipping the mixer only for str/tuple (already
siphash-mixed by CPython) would need a per-call type branch costing about
what it saves. Keep the double hash; this lever is closed.
